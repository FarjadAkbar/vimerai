VimeraAI


Product Overview
VimeraAI is a long-term SaaS platform for AI video generation. The goal is to build a sustainable company, not a fast MVP.
Phase 1 is focused on fast video generation for social media creators.
Core principles:
•	Operational safety
•	Cost control under worst-case usage
•	No provider exposure in UI
•	Clean and simple UX
•	Long-term scalability




Decisions Log

All major product and technical decisions must be written here. No decision is considered final unless documented in this log.
Decision #001 – Primary User Persona
The primary user persona for VimeraAI at launch is: Fast Mode users (social media content creators and marketers).
Reason:
•	Fast purchase decision
•	High usage frequency
•	Clear and urgent pain point
•	Strong early cash flow potential
Cinematic Mode is positioned as a WOW differentiator and premium capability, not the initial entry point.
Avatar Mode is planned as a later vertical expansion.
The developer is responsible for implementation only.
The following decisions are locked and cannot be changed without explicit approval:
•	Pricing structure and plans
•	User flow (First 60 seconds)
•	Smart Preview logic
•	Mode positioning (Fast as default)
•	Subscription limits and usage logic
•	No free full video generation
•	No provider exposure in UI
•	Language switch behavior (text only)
The developer may choose:
•	Frontend framework
•	Backend framework
•	Database structure
•	UI component implementation
•	Code organization
Any feature addition, removal, or logic change requires written approval.
Additional Technical Safeguards
•	The developer must not have access to final production API keys.
•	All non-Phase 1 features must be implemented behind feature flags.
•	No user-generated content (prompts or inputs) should be logged, stored, or analyzed unless required for system operation.
Decision #003 – Security & Abuse Rules
Basic abuse prevention rules for Phase 1:
•	Preview is limited to one attempt per account.
•	Generation requests are rate-limited.
•	Video generation is blocked when usage limit is reached.
•	Failed generations do not deduct usage unless output is delivered.
•	Temporary blocking is allowed for suspicious activity.
•	Detection and enforcement may be added in later phases if required
Additional Security Enforcement Notes
•	Rate limiting must be implemented to limit excessive generation or preview requests within short time windows.
•	Rate limiting should not be noticeable for normal users.
•	Soft blocking is preferred over permanent bans in Phase 1.
•	Temporary blocks must display a clear and respectful message to the user.
•	System logs must be limited to technical and operational errors only.
•	User-generated content (prompts or inputs) must not be logged or stored.
Final authority for launch readiness and timing remains with the product owner.

Provider Independence & Future-Proof Architecture (Mandatory)
This project must be implemented with full provider independence.
All video generation logic (Fast, Cinematic, Avatar) must be abstracted behind internal interfaces and must not be directly coupled to any third-party AI provider in the codebase, architecture, or business logic.
The platform must be designed so that AI providers can be replaced, combined, or partially substituted in the future without requiring changes to the user experience, frontend, or core application logic.
No third-party provider names, SDK-specific logic, or provider-dependent assumptions should appear in the core generation flow. Each provider must be implemented as a replaceable adapter only.
This requirement is non-negotiable, as it is critical to the long-term sustainability, security, and strategic independence of the platform.
